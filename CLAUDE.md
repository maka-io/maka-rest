# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

`maka:rest` — a **server-only Meteor package** (not an npm package; there is no `package.json`) that
mounts an authenticated REST API onto `WebApp.connectHandlers`. Source is TypeScript under `lib/`,
compiled by Meteor's own `typescript` package at build time. Published to Atmosphere.

## Build / test / release

The Meteor toolchain compiles the package; there is no separate build step. Tests are mocha, run
server-side through `meteortesting:mocha`:

```bash
# full suite, headless
TEST_CLIENT=0 meteor test-packages ./ --once \
  --driver-package meteortesting:mocha --port 3200

# one file or one case
MOCHA_GREP='getPathname' TEST_CLIENT=0 meteor test-packages ./ --once \
  --driver-package meteortesting:mocha --port 3200

meteor publish                   # after bumping version in package.js
```

- `TEST_CLIENT=0` is required: the package is server-only, and without it the runner waits for a
  browser to connect. Do **not** set `TEST_WATCH=0` — that field is truthiness-checked, so the
  string `"0"` turns watch mode *on*.
- **On Windows the tool does not return to the shell after the summary prints.** Results are
  complete once you see the `N passing` summary followed by `SKIPPING CLIENT TESTS`; everything
  after that is the tool failing to shut down. Wrap it in `timeout` and read the output rather than
  trusting the exit code. A killed run can orphan the test mongod on the port above the app's
  (3201 for `--port 3200`) — kill it before the next run or the port is taken.
- The suite is fully green (103 passing, nothing pending). No test currently pins known-wrong
  behaviour; if one ever does, say so in a comment above it.
- `tsconfig.json` is for editor/IDE type hints only. Standalone `tsc` will not resolve `meteor/*`
  imports or the `Npm.depends` modules (they live in Meteor's `.npm/package/node_modules`).
- Releasing means editing `version` in `package.js`; `.versions` is regenerated by Meteor.

Test layout: `test/_fixture.ts` is loaded first and is the **only** file that constructs a
`MakaRest` instance — it sets `MakaRest.auth.loginType` before doing so, because the
`MakaRest.Settings` latch means the first instance in the process decides whether the default auth
endpoints ever exist. It also exports a raw `http.request` helper; `fetch` normalises the path
before it reaches the wire, which would silently defeat the dot-segment tests. Unit tests build a
`Route` against a literal stand-in api to stay clear of those process-wide latches.

## Adding a file to `lib/`

If a new `lib/*.ts` file is reached by a **relative import** (rather than only through
`api.mainModule`), it must also be listed in the `api.addFiles([...], 'server')` array in
`package.js`. Otherwise it is silently dropped when the package is consumed as a pre-built isopack
and recompiled downstream. `package.js` carries a comment explaining this; do not "clean up" that
array.

## Architecture

Five modules, layered:

- **`lib/maka-rest.ts`** — the `MakaRest` class (default export) plus `Restivus` and `Codes`
  re-exports. Holds per-instance config, the global interceptor list, the static `MakaRest.auth`
  hook registry, and the built-in `login` / `logout` / `logoutAll` endpoints.
- **`lib/route.ts`** — `Route`: resolves endpoint shorthand, merges route-level into endpoint-level
  options, applies rate limiting, runs auth + role/scope checks, and registers the handler.
- **`lib/json-routes.ts`** — `JsonRoutes`, a **singleton** router installed on
  `WebApp.connectHandlers`. Owns JSON body parsing, middleware chain, path matching, and
  `sendResult`.
- **`lib/auth.ts`** — `Auth`: password login against `Meteor.users`, token generation. Pure static
  methods, no HTTP knowledge.
- **`lib/codes.ts`** — `Codes` static factories (`success200`, `notFound404`, …) producing the
  `StatusResponse` shape `{ statusCode, status, data, headers?, extra? }`.

### Request flow

```
WebApp.connectHandlers
  → MakaRest.executeInterceptors   (static, global across all instances)
  → JsonRoutes.processRoutes       (only URLs starting with /<apiRoot>)
  → parse JSON body → middleware chain → matchRoute
  → Route handler: rate limit → build EndpointContext → _callEndpoint
       → _authenticate (config.auth.user → token → Meteor.users lookup)
       → _roleAccepted (Roles.userIsInRole [+ scopeRequired])
       → endpoint.action(context)
  → JsonRoutes.sendResult
```

### Invariants that bite

- **Endpoints must return a `StatusResponse`.** `Route._callEndpoint` throws
  `'Endpoint response must contain a statusCode and data'` for anything with a missing `statusCode`
  or `data`. Return a `Codes.*` helper. A falsy return becomes `Codes.noContent204()` (204).
- **Path composition** is `<apiRoot>/<version>/<apiPath>/<path>`, built in `normalizeApiPath`.
  `addRoute(path, { onRoot: true }, …)` bypasses version/apiPath and mounts at `<apiRoot>/<path>`.
  `apiPath` is required unless the instance is constructed with `isRoot: true`.
- **`MakaRest.Settings`** is a module-level singleton enforcing two global rules: only one `isRoot`
  instance may exist, and the default auth endpoints are registered exactly once across all
  instances. Consequence: `MakaRest.auth.loginType = 'default'` must be set **before** the first
  `new MakaRest(...)`, or the login routes are never created.
- **Interceptors and auth hooks are static**, so they are shared by every `MakaRest` instance in the
  process (i.e. across API versions).
- **A Meteor package export is not a runtime global.** A bare identifier in `lib/` resolves against
  `globalThis`, where package exports do not appear, so it is `undefined` no matter what the
  consuming app has added. The demonstration is `Accounts`: `accounts-base` and `accounts-password`
  are installed in the test app, and `Accounts` was still `undefined` inside package scope until it
  was imported from `meteor/accounts-base` and declared in `Package.onUse`. Installing a classic
  `api.export` package app-side does not put its symbol in another package's scope.
- **The verified-email gate is global and read at request time.**
  `MakaRest.auth.requireVerifiedEmail` makes every endpoint with `authRequired` also require the
  user to hold an `emails` entry with `verified: true`. It is read inside `Route._verifiedEmailAccepted`
  on each call, so unlike `loginType` there is no latch and no ordering rule -- which is also what
  lets tests toggle it in `afterEach`. It **fails closed**: no `emails` array, or an empty one, is a
  denial, so username-only accounts are locked out of every authenticated route when it is on.
  Denial is `403` with the body `"Email address must be verified"`, not `401`, and it is checked
  *before* `_roleAccepted` so an unverified user cannot trip that method's missing-package throw.
  The built-in `logout`/`logoutAll` routes carry an internal `_skipVerifiedEmailCheck: true` route
  option so a session stays terminable; it is not a public per-route override, and none exists.
  This is also the first *runtime* use of the `MakaRest` binding inside `route.ts` -- the two modules
  import each other, and until this landed `MakaRest` was a type-only reference there. It resolves
  because the read happens per request, long after both modules finish loading.
- **`roleRequired` reaches `alanning:roles` through the `Package` registry**, never as a scope
  symbol. It is a **weak** dependency, so an app that never uses `roleRequired` need not install it;
  `Route.resolveRoles()` reads `Package['alanning:roles'].Roles` at call time and throws a named
  error when it is absent. `_roleAccepted` is `async` and calls
  `userIsInRoleAsync`/`getScopesForUserAsync` — the sync `userIsInRole`/`getScopesForUser` are
  **client-only** in v4 and simply do not exist on the server. `_callEndpoint` must keep awaiting
  it: a promise is always truthy, so dropping that `await` turns every role denial into a pass.
  `Package.onTest` pins `alanning:roles@4.0.0` explicitly — the bare name makes the solver trip over
  an ancient 1.0.6 catalog entry and silently omit the package.
- **Accounts internals are async on Meteor 3.** `Accounts._checkPassword` no longer exists (use
  `_checkPasswordAsync`), and `_insertHashedLoginToken` returns a promise that must be awaited or
  the login token is handed out before it is persisted. `_generateStampedLoginToken` and
  `_hashLoginToken` are still synchronous. `Package.describe`'s summary still claims "Meteor 2.13+",
  but `api.versionsFrom(['3.5'])` and these APIs make it 3.x-only.
- **Route matching is exact-segment**, not Express-style: `JsonRoutes.matchRoute` requires equal
  segment counts and only treats `:`-prefixed segments as variable. `*` has no special meaning, so
  the catch-all routes registered by `initializeWildcardRoutes` never match; unmatched requests
  under `/<apiRoot>` fall through to `JsonRoutes.routeRequest`'s own plain-text 404.
- `Route.addToApi` unconditionally overwrites `endpoints.options` with
  `config.defaultOptionsEndpoint`, so a per-route `options` endpoint passed to `addRoute` is ignored.
- **There is no `{status, data}` envelope on the wire.** `JsonRoutes.sendResult` writes the
  `StatusResponse`'s `data` value as the entire body, so `Codes.success200({id: 1})` sends
  `{"id":1}`. The envelope shown throughout the README is not what the code produces.

## README accuracy

`README.md` is the user-facing doc and parts of it predate v4. Where they disagree, the code wins —
notably the constructor options (the code uses `apiRoot` + `version` + `apiPath` / `isRoot`, not the
README's `apiPath: 'api/'`), and endpoint return values (the code requires `Codes.*` responses, while
several README examples return raw strings or plain objects). Update the README alongside behavior
changes; `CHANGELOG.md` has not been maintained since the Restivus fork (v0.8.x) and is effectively
historical.
